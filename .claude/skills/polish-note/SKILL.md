# ノートを推敲する

notes/*.md の内容そのもの（技術的な正しさや構成）ではなく、**文体と日本語表現**のレベルで、このリポジトリの
慣行に揃える。CLAUDE.md に明文化された規則と、既存ノートから読み取れる暗黙の慣行の両方を対象にする。

対象外にすること:

- 記事の内容が事実として正しいかどうかの検証（裏取りは著者が済ませている前提）。
- ノートの分割・統合そのものの実行（1ノート1概念の原則に反していそうなら指摘はするが、切り出すかどうかは
  著者の判断を仰ぐ）。

## 進め方

1. 対象ノートを読む。用語の表記ゆれなど複数ファイルにまたがる指摘をするために、必要なら notes/*.md 全体を
   `grep -rn` で横断して確認する。
2. 下記のチェック観点で指摘を洗い出す。「該当箇所 → 問題 → 修正案」の形で1つずつまとめる。
3. 修正案を提示し、著者の承認を得てから Edit で反映する。著者の語彙選択や言い回しの個性はそのまま残し、
   規約に反する部分だけを直す。AI が書きがちな一般論への言い換えで上書きしない。
4. 修正したら、その節だけでなくノート全体を読み返す（CLAUDE.md 原則6）。見出しの順序や重複、話の流れの
   ずれも確認する。

## チェック観点

### 文体・トーン

CLAUDE.md の「書き方のトーン」を実務チェックに落としたもの。

- **敬体（です・ます）が混じっていないか。** このリポジトリのノートは常体・体言止めで統一されている
  （ざっと数えると `だ。`/`である。` に対して `です。`/`ます。` はほぼ出てこない）。「〜してみましょう」
  「〜だと思います」のような読者への語りかけも使わない。自分用の記録であって、読者への説明ではない。
- **評価的・煽情的な言い回しがないか。** 「劇的に」「驚くほど」「画期的な」のような形容・誇張は削る。
  出典（英語記事など）がそう書いていても、そのまま見出しや地の文に持ち込まず、背景にある客観的な事実だけを
  抽出する。
- **推測と事実が区別されているか。** 「〜と思われる」「（推測）」のような明示があるか確認する。裏の取れない
  ことを断定形で書いていないか。
- **冗長な言い換え・前置きがないか。** 同じ内容を2度説明していたら削る。足し算ではなく引き算で読みやすさが
  上がる箇所を優先して指摘する。

### 日本語表記

既存ノートの実測パターンに基づく。

- **数字 + 助数詞はスペースなしで詰める。** `1つ`、`9件`、`2026年`、`30秒` のように、半角数字と助数詞
  （つ・件・回・年・月・日・分・秒・倍・割・% など）の間にスペースを入れない。ここは既存ノートで一貫している。
- **英単語・製品名と日本語の間は、名詞句の境界でスペースを入れる。** 例: `Gleam コンパイラ`、`Wasm 命令列`、
  `SVG パス`。ただし直後に日本語の助詞・活用語尾が続く場合は密着させる。例: `URLに`、`Workerが`、
  `Cloudflareの`、`hydrateされる`。「名詞+名詞はスペース、名詞+助詞は密着」を基準にして、迷ったら `grep` で
  類例を探し既存の書き方に合わせる。
- **インラインコード（`` `foo()` ``）も英単語と同じ扱いにする。**
- **半角英数字を使う。** 全角の英字・数字（Ａ、１など）は使わない。
- **英語フレーズをその場でカタカナへ直訳した複合語を作らない。** ソースや実装が独自に作った造語（例:
  `KNOWN_HOLES` の "silent hole"）を意味を汲まずに音だけカタカナへ移すと、「ホール」のように日本語では
  別の意味（hall=会場）が先に立つ語と衝突し、読んでも意味を推測できない語になる。判断基準は「その語だけ
  見て、英語を知らない読者が意味を推測できるか」。できないなら、(a) 同じノートで実際に英語のまま使われて
  いる類語（`trichotomy` など）に倣って英語のまま残すか、(b) 意味を汲んだ自然な日本語に言い換えて初出だけ
  英語原語を括弧で添える（例: 大声で（loud）、静かに開いた穴（silent hole））。同じノートの中で片方だけ
  英語のまま、もう片方だけ独自にカタカナ化するような不統一も避ける。キャッシュ・フォールバック・
  ミドルウェアのように既に定着した借用語まで英語に戻す必要はない。
- **同じ概念には同じ用語を通す。** ノート内、および `[[...]]` で繋がる既存ノートとの間で表記ゆれ（例:
  「フォールバック」と「フォールバック処理」の混在）がないか確認する。

### 構造（軽く確認する程度。深入りしない）

- `[[...]]` で繋げるべき概念がプレーンテキストのままになっていないか（CLAUDE.md 原則3）。
- 2つ目の話題が育ってきていないか（原則1）。育っていたら切り出しを提案するに留め、実行は著者の判断を仰ぐ。
- `## 理解度チェック` の quiz が「その場で調べれば分かる事実」ではなく「実際に動かして分かったこと・間違え
  やすい点」を問えているか（CLAUDE.md「理解度チェック」節）。1問1点になっているか。

## 参考にした知見

- 日本語と英数字の間のスペーシングを判断基準として明文化する発想は、[azukiazusa/skills の
  write-blog-article スキル](https://github.com/azukiazusa1/skills/blob/a7f996f1cd700a4a56827f6cf2a130ff5a9ceedf/skills/writing/write-blog-article/references/azukiazusa-style.md)
  の Japanese formatting 節から借りている。ただしそこでは数字と助数詞の間にもスペースを入れる例
  （`2 つ`）になっており、このリポジトリの実測（`2つ`）とは異なる。ルールは既存ノートの実測に合わせて
  上書きしてある。
- 「足し算より引き算」「体験や固有の観測を材料にする」という編集姿勢は、
  [AIとテクニカルブログ記事を書いて学んだこと](https://azukiazusa.dev/blog/what-i-learned-writing-technical-blog-posts-with-ai)
  から。AI が書きがちな一般論への言い換えを削り、実際に手を動かして得た具体的な観測（コマンド・バージョン・
  出力）を残す、という判断基準として使う。
