# ノートの日本語を整える

ノートの核を変えず、誰が何を確かめ、どこまで言えるのかを読み取れる文章にする。表記・文体の慣行（常体、
数字と助数詞の詰め方、英単語との間のスペース、独自訳語の禁止）は [polish-note](../polish-note/SKILL.md)
が持つので、ここでは文の意味と流れを扱う。

## 意味を保つ推敲

本文は常体を基本とし、見出しやコードの説明まで無理に文末を揃えない。専門用語は想定読者（あとから読み返す
自分）に合わせ、初出で説明する。

主語、対象、理由と結果の関係が曖昧な箇所を直す。一文に複数の判断が入っていれば分け、補足は必要な位置へ
移す。抽象的な評価は、資料や観察が支える具体的な説明に置き換える。情報が不足しているときは、滑らかな文章で
埋めず、不明点や未検証の範囲を残す。

推敲前後で意味を照合する。特に「確認した」「資料に記載がある」「推測する」「未検証」を入れ替えない。
限定条件、否定、数値、単位、バージョン、日付、引用の帰属を落とさない。AI によるツールの操作を人間の生活
体験のように書き換えない。

コード、API 名、パス、コマンド、URL、実出力は技術資料として扱い、語感だけで修正しない。明らかな誤記でも
根拠を確認し、コードを変更したなら必要な検証をやり直す。

## 読み手が迷う箇所をセルフレビューする

本文全体を読み、次を確認する。表記だけでなく、段落間の理由のつながりも推敲する。

- 見出しが内容や行動を具体的に示しているか。「根拠と検出力を確かめる」のような抽象語の組合せより、
  「テストを一つ選び、見つけてほしい間違いを入れてみる」のような動作を優先する。
- 技術識別子の指す場所が分かるか。`value` とだけ書かず、`<TotalReadout value={total()} … />` のように
  部品名と変更箇所を示し、親から子に渡す金額だと説明する。省略記号を含む説明用コードと実行可能なコードは
  区別する。
- 専門用語の意味を先に説明したか。「意図的な間違いを加えたコード（ミュータント）」を導入し、「元のコードで
  通り、変更後で落ちるテスト」を説明してから「死滅させる」と呼ぶ。
- 検証報告が唐突に挿入されていないか。「この検査では計算結果は分からない。そこで別途…」のように、未確認の
  対象と次の確認をつなぐ。
- 主張を読み流しても拾えるか。太字は持ち帰ってほしい理解と具体的な行動に絞る。数値・固有名詞を機械的に
  太字にしたり、段落全体を強調したりしない。
- 結びが定型的なまとめや呼びかけになっていないか。ノートは `## 理解度チェック` → `## 出典` → タグで終わる
  ので、その前に「まとめ」の節を足さない。

推敲で意味を広げない。たとえば「値が同じになる条件では取り違えを見逃す」を「値のテストでは取り違えを
検出できない」に変えない。今回の例で数量5・合計500なら値比較でも検出できる、という限定を保つ。

## 再現できる材料を保つ

同じ評価の反復や脇道の説明を整理する。再現に必要な手順、前提、コマンド、バージョン、実際の出力、変更箇所、
期待する結果は削らない。結論を強く見せるために保証や根拠のない性能表現を足さない。

次はノートの機構なので、推敲の対象にしない。

- `[[slug]]` / `[[slug|表示]]` のウィキリンク、最終行の `#tag`、`## 理解度チェック` の `quiz` ブロックの
  区切り（`---`）、` ```canvas ` の JSON、frontmatter。
- コードブロックとインラインコードの中身。
- `## 出典` の URL と、出典が誰の言葉かを示す帰属。

依頼された文章の編集範囲にとどめる。このスキルは外部投稿や公開の権限を追加しない。私的会話や内部の指示を
文章例に転載しない。
