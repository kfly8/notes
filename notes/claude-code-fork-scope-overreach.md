# Claude Codeのforkサブエージェントは委任範囲を超えて操作することがある

Claude Codeの`Agent`ツールを`subagent_type: "fork"`で呼ぶと、呼び出し元セッションの会話コンテキスト全体(それまでの会話・承認済みの計画・完了済み作業の詳細)を引き継ぐ。加えて`isolation: "worktree"`を指定しない限り、**forkは親セッションと同じgit作業ディレクトリを共有する。** この2つが組み合わさると、狭いタスクだけを渡したはずのforkが、継承したコンテキストから「最終的にはこうする計画だった」と読み取り、明示的に指示していない操作まで自分で実行することがある。

## 再現した状況

- 承認済みの計画に「最終的に複数のPRをスタックして作る」という記述がある。
- その計画の最後の工程(コメント整理)を、複数の並列forkに分担させた。各forkへの指示は「このファイル群を直して、テストを通して報告して」だけで、`git push`やPR作成は一切指示していない。
- 最後に完了したforkが、他のforkの変更を1つのコミットにまとめ、`git push`でリモートに全ブランチを送り、`gh stack submit`相当の操作で実際にPRを作成した。
- push・PR作成はどのforkにも明示的に指示していない。

## なぜ起きるか

forkは「このタスクだけやって」という指示文とは別に、会話全体の目的(承認済みの計画)を認識している。作業ディレクトリが共有されている、つまり技術的にpushやPR作成が可能な状態にあることと相まって、「次にやるべきことは明らかだから、やっておく方が親切だろう」という方向に外挿しやすい。指示文に「やってよいこと」しか書かれておらず「やってはいけないこと」が書かれていない場合、この外挿を止める材料が無い。

## 実害の評価軸

今回のケースでは以下がたまたま実害を抑えていた。

- 作成されたPRはdraftのままだった。
- CIはpushトリガーのworkflowしか無く、PRトリガーの検証は走らなかった。
- 差分の中身自体は承認済み計画通りで正しかった。

裏を返すと、これらが揃っていなければ(ready for reviewで作成される、PRトリガーのCIがある、内容に誤りがある)実害はもっと大きくなり得た。「pushやPR作成のような可逆性が低い/外部から見える操作は、明示的に依頼されたときだけ行う」という原則が、fork経由だと素通りしうる。

## 対策

1. **forkのプロンプトで境界を明示する。** 「この変更に留め、コミット・push・PR作成はしないこと」まで書く。省略すると「書いていないから禁止ではない」と解釈される余地が残る。
2. **push/PR作成のような最終ステップは、forkにやらせず親セッション自身が行う。** 複数forkの結果を集約して最終操作をするのは、常に人間の確認を経由できる立場(親セッション)の役割にする。
3. `isolation: "worktree"`を指定すればforkは隔離されたgit worktreeで動くため、親のブランチへ直接pushする経路自体が無くなる。ただしforkが親と同じ作業ディレクトリの最新状態を見る必要があるタスクでは使いにくいトレードオフがある。
