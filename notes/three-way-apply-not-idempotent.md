# base → next の差分を当てる処理は、2回当てると壊れる

手元で編集した内容を、他の人の変更で先に進んでいるかもしれない共有状態へ取り込むには、「編集を始めたときの状態（base）」と「編集後の状態（next）」を送り、受け手が base から next への差分だけを今の状態に当てる。変わっていない部分には触らないので、その間に他の人が変えた箇所は残る。git の3-way マージと同じ考え方で、ima（現在の [[pedit]]）の [[json-canvas-co-editing-text-or-structure|JSON Canvas の共同編集]]では、ファイルの外部編集とブラウザでの JSON 手編集の両方をこの形で取り込んだ。

ただし、この当て方は冪等ではない。ネットワーク越しに使うと、同じ差分が2回当たる場面と、同じ base から作った差分が続けて当たる場面がそれぞれ起きる。

## 当て方

ima の `canvas.Apply` がしていることは次のとおり。

- ノードとエッジは `id` で突き合わせる。
- base と next で値が変わったフィールドだけを設定する。変わっていないフィールドは、今の状態が何であっても触らない。
- 本文（テキスト）は文字単位の差分にして、今のテキストに当てる。前後の一致部分から位置を写すので、他の人の入力が別の場所にあれば両方残る。
- base にあって next にない要素は削除し、next で増えた要素は追加する。
- 他の人がすでに消した要素を next が変えていても、その削除を優先する。

## 同じ差分を2回当てると、挿入が重なる

フィールドの設定は2回やっても結果は同じだが、テキストの差分は違う。base の `Hello` から next の `Hello there` への差分は「5文字目の後に ` there` を挿入」なので、1回目の後の `Hello there` にもう一度当てると挿入がまた起きる。

実際に、同じ base・next を2回当てた結果は `"Hello there there"` になった。

これが問題になるのは再送のとき。送った編集の返事が来ないまま接続が切れた場合、送り手からは「届かなかった」のか「届いて当たったが、返事だけが失われた」のか区別できない。後者のときに再送すると2回当たる。

ima では、編集ごとに部屋の中で一意な id を付け、受け手（ホスト）が直近に当てた id を256件まで覚えておくようにした。覚えている id が再び届いたら、当てずに「当てた」とだけ返す。そのため id は、部屋の中で一意なランダム値でなければならない。もし2人が同じ id を使うと、2人目の編集が黙って捨てられる。

## 同じ base から作った差分を続けて当てると、先の挿入が重なる

返事を待たずに次の編集を送ると、2つ目の差分も同じ base から作られる。`Hello` を base にして A（`Hello there`）と B（`Hello there friend`）を送り、この順に当てると、B の差分には A と同じ ` there` の挿入が含まれているので、`"Hello there friend there"` になった。

B の base を A の next（`Hello there`）にして当てると、結果は正しく `"Hello there friend"` になった。

これは再送のときに限らない。返事が戻る前に次の編集を送れば、接続が安定していても起きる。ima のブラウザ側では「返事を待つ編集は同時に1つだけ」にし、返事が来たら base をそのとき当たった内容に進めてから、その間に書かれた分を送るようにした。再送も、この1つを同じ id で送り直すだけになる。

## 理解度チェック

```quiz
返事のない編集を、接続が戻ったあとに新しい id で送り直すと何が起きうるか。
---
元の編集が届いて当たっていて返事だけ失われていた場合、同じ差分がもう一度当たり、テキストの挿入が重なる（`Hello there there`）。
```

```quiz
同じ base から作った編集 A と B を順に当てると、なぜ A の挿入が重なるのか。
---
B の差分は base から作られているので、A がすでに入れた変更も含んでいるから。B の base を A の next にすれば重ならない。
```

```quiz
受け手が id で重複を捨てるとき、送り手の id に何が求められるか。
---
部屋（受け手が見るすべての送り手）の中で一意であること。重なると、別の人の編集が当たらないまま「当てた」と返される。
```
