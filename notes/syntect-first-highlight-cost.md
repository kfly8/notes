# syntectの初回ハイライトが遅い理由

Rust のシンタックスハイライトライブラリ syntect は、アプリ起動後の最初のハイライトだけが遅い。原因は2つある。

1. **シンタックスセットの構築。** 既定の言語定義一式(peitho-core では `two_face` の `extra_newlines()` に独自定義を足してビルド)を1回組み立てる
2. **正規表現の遅延コンパイル。** 言語定義の正規表現は、初めて使われたときにコンパイルされる(docs.rs: "Lazily compiles regexes on first use to improve initialization time.")。言語ごと、さらにその言語の中でも実際に当たったパターンごとに、初回だけコストがかかる

どちらも一度払えば、以後は同じプロセス内でほぼゼロになる。

## 実測

peitho-core(syntect 5、`default-fancy` feature で fancy-regex を使う)を組み込んだアプリで測った。対象は sh/js/tsx/html のコードブロックを含む14枚のデッキ。

| | debug | release |
|---|---|---|
| シンタックスセット構築 | 約2.0秒 | 約0.28秒 |
| デッキの初回レンダリング | 約3.1秒 | 約0.26秒 |
| 2回目以降のレンダリング | 約0.09秒 | 約0.01秒 |

1ブロックだけの初回ハイライト(debug): tsx 1.36秒、js 0.40秒、sh 0.30秒。release: tsx 109ms、js 35ms、sh 20ms。

debug が約10倍遅いのは、syntect や正規表現クレートが最適化なしでビルドされるため。[[cargo-dev-profile-optimize-dependencies]] で依存クレートだけ最適化すると、debug でも release 並み(構築0.28秒+初回0.30秒)になった。

## 起動時に温める

初回コストを、ユーザーが操作する前にバックグラウンドのスレッドで払っておく。何で温めるかで効果が変わった。

依存クレートを最適化した debug ビルドで、対象デッキの初回描画(シンタックスセット構築込み)を測った。

| 温め方 | 温めにかかった時間 | その後の対象デッキの初回 |
|---|---|---|
| なし | - | 約570ms |
| シンタックスセットの構築だけ | 約0.27秒 | 約290ms |
| 対象を含む最近のデッキ3件をそのまま描画 | 約0.6秒 | 約13ms |

別の計測で、17言語の短いサンプルコードで温めた場合は、release で対象デッキの初回が 0.26秒→0.08秒にとどまった(2回目以降の0.01秒には届かない)。短いサンプルでは、実際のコードが通るパターンの一部しかコンパイルされない。「次に開きそうなもの」(最近開いたファイルなど)を実際に処理して結果を捨てると、必要な正規表現がちょうどコンパイル済みになる。実ウィンドウでも、起動直後に最近のデッキを開くまでの時間が約615msから約55msになった。

代償は、起動のたびにバックグラウンドで CPU を使うこと。温めが終わる前に開いた場合は、それまでに済んだ分だけ速くなる。

## 理解度チェック

```quiz
syntectで、同じ言語の2ブロック目のハイライトが1ブロック目より速いのはなぜか?
---
言語定義の正規表現は初めて使われたときにコンパイルされ、以後は同じプロセス内で使い回されるから。
```

```quiz
起動時の温めに、主要言語の短いサンプルコードではなく、最近開いたファイルをそのまま処理する方が効くのはなぜか?
---
正規表現はパターンごとに遅延コンパイルされるので、短いサンプルでは実際のコードが通るパターンの一部しかコンパイルされない。実際のファイルを処理すれば、その内容が使うパターンがすべて済む。
```
