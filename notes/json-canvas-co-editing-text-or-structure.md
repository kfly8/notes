# JSON Canvas の共同編集は、テキストで持つか構造で持つか

[[json-canvas]] を CRDT で共同編集するとき、共有する単位は2通りある。ファイルの文字列をそのまま Y.Text で持ち、キャンバスの画面はそのパース結果として描く（テキストで持つ）か、ノードとエッジを Y.Map の Y.Array として持ち、ファイルは構造から書き出す（構造で持つ）か。ima（ローカルのファイルをブラウザで共同編集する CLI。現在の [[pedit]]）で両方を比べ、構造で持つ方を選んだ。

## テキストで持つと、キャンバスだけの操作でも JSON が壊れる

Y.Text は文字単位でマージするので、JSON の文法を知らない。キャンバスの操作を「値の範囲の書き換え」にして差分を小さくしても、同時編集の組み合わせによっては壊れる。Y.Doc を2つ作り、それぞれで編集してから互いの更新を当てる形で確かめた（Yjs 13）。

- **削除されたノードの中への書き込みが残る。** 一方がノードを行ごと消し、もう一方が同じノードの本文に文字を足すと、Yjs は「削除された範囲への挿入」を残すので、消えたはずの場所に文字だけが浮く。
- **区切りのカンマを両方が消しにいく。** 配列から要素を消すとき、先頭以外は「前のカンマ」、先頭は「後ろのカンマ」を一緒に消す。`[{"id":"a"},{"id":"b"},{"id":"c"}]` の `a` と `b` を2人が同時に消すと、両方が同じカンマを自分の分として消し、`[,{"id":"c"}]` になった。
- **数字が連結される。** `{"x":0}` の `0` を一方が `10`、もう一方が `20` に同時に書き換えると、`0` の削除は1回で済み、挿入は両方残って `{"x":2010}` になった（どちらが先に並ぶかはクライアント ID で決まる）。JSON としては正しいので、壊れたことを検出できない。

1ノードを1行に書く Obsidian の書式なら、別々のノードへの編集は別々の行に落ちて衝突しにくい。ただし上の3つは同じノード・隣り合うノードの操作で起きるので、書式では防げない。

構造で持てば、同じ値を同時に書き換えても後から届いた方が勝つだけで、文法的に壊れた状態そのものが存在しない。本文は Y.Map の中の Y.Text にしておけば、同じノードへの同時入力も文字単位でマージされる。

## 決め手は「誰がテキストを触るか」

テキストで持つ利点は、テキストのまま編集できるという JSON Canvas の良さを保てること。生の JSON エディタとキャンバスの画面から同じ Y.Text を同時に編集でき、ファイル形式ごとの仕組みも要らない。

この利点が効くのは、JSON を直接編集する人が多い場合に限られる。キャンバスでの編集が主で、JSON の直接編集は一括置換や壊れた箇所の修正のような、一人で短時間やる作業に限られるなら、利点はほぼ残らず、欠点（キャンバスだけ使っていても壊れる）だけが残る。しかも壊れたときに直す手段は JSON の手編集しかないので、その用途では目立たせない裏口に頼ることになる。ima はこの使い方だったので、構造で持つ方を選んだ。

テキストで持ったまま「JSON が不正な間はキャンバスを読み取り専用にする」という規則を足すと、JSON の入力途中の不正には対応できる。ただし、これはテキストとキャンバスの混在を安全にするだけで、キャンバス同士の同時編集で壊れる問題は残る。

## 構造で持ったときの JSON の裏口

構造で持つと、生の JSON エディタは同じ Y.Text に結べない。ima では、ブラウザ側の JSON は手元だけで編集し、正しい JSON になるたびに「編集を始めたときの JSON（base）」と「今の JSON（next）」をホストに送る形にした。ホストはそれを、ファイルが外部で書き換えられたときと同じ処理（base から next への差分を、今の構造に当てる）で取り込む。差分の処理は Go 側に1つだけ置けば済む。

```canvas
{
  "nodes": [
    {"id": "pane", "type": "text", "x": 0, "y": 0, "width": 240, "height": 60, "text": "ブラウザの JSON ペイン\n（手元だけで編集）"},
    {"id": "file", "type": "text", "x": 300, "y": 0, "width": 240, "height": 60, "text": "ホストのファイル\n（外部のエディタで編集）"},
    {"id": "host", "type": "text", "x": 150, "y": 160, "width": 240, "height": 60, "text": "ホスト: base → next の差分を\n構造に当てる", "color": "4"},
    {"id": "doc", "type": "text", "x": 150, "y": 300, "width": 240, "height": 60, "text": "共有ドキュメント\n（Y.Array の Y.Map）"}
  ],
  "edges": [
    {"id": "e1", "fromNode": "pane", "fromSide": "bottom", "toNode": "host", "toSide": "top", "label": "{base, next}"},
    {"id": "e2", "fromNode": "file", "fromSide": "bottom", "toNode": "host", "toSide": "top", "label": "変更の検知"},
    {"id": "e3", "fromNode": "host", "fromSide": "bottom", "toNode": "doc", "toSide": "top"}
  ]
}
```

強調した箱が差分を当てる唯一の場所。入力途中の不正な JSON はペインの中だけの状態になり、他の人には届かない。当てる処理には再送まわりの落とし穴がある（[[three-way-apply-not-idempotent]]）。

構造からファイルへ書き戻すときは、元の書式を保つ必要がある（[[json-layout-preserving-rewrite]]）。Go（ygo）と JS（Yjs）で同じ構造を扱うときの注意は [[ygo-yjs-nested-types]] に、画面側で使った `@barefootjs/xyflow` の注意は [[barefootjs-xyflow-csr-gaps]] にまとめた。

## 理解度チェック

```quiz
JSON Canvas を Y.Text で共有したとき、一方がノードを削除し、もう一方が同時にそのノードの本文を編集すると何が起きるか。
---
Yjs は削除された範囲への挿入を残すので、消えたノードの位置に編集した文字だけが残り、JSON が壊れる。
```

```quiz
同じノードの `"x":0` を2人が同時に `10` と `20` に書き換えた。Y.Text で持つと何が問題になるか。
---
`0` の削除は1回、挿入は両方残るので `"x":2010` のような値になる。JSON としては正しいので壊れたと検出されない。
```

```quiz
構造で持つ場合、ブラウザで編集した生の JSON をどう取り込むか。
---
編集を始めたときの JSON（base）と今の JSON（next）をホストに送り、ホストがファイルの外部編集と同じ処理で base から next の差分を今の構造に当てる。
```
