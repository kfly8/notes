# カバレッジ床 — レビューでしか守れないルールを機械化する

「〜を追加するときはテストも同じ PR に入れること」のような**文章ルールをレビューだけで守る運用は、必ず抜ける**。守らせたい対象が列挙可能になっていないことがサインで、対処は列挙可能にしてから、列挙に対して床（floor）を張ること。3つの部品からなる。

1. **分母 = 正のレジストリ。** 受理するものを定数配列として具象化し、型の網羅性ピンを付ける。対象の union を広げてレジスタし忘れるとコンパイルエラーになる。
2. **分子 = 宣言ではなく計算。** どの fixture が何をカバーしているかは、fixture を実際にコンパイル・解析して機械的に導出する。手で書いた対応表は必ず実態とドリフトするが、コンパイラが手元にあるならその parse 結果こそが対応表になる。
3. **床テスト。** 分母の全メンバーについて「カバーする fixture がある」か「理由付きで allowlist に載っている」かを要求する。allowlist は**縮小専用**にする: 載っているメンバーがカバーされた瞬間に stale としてテストが落ち、エントリの削除（graduation）を強制する。

## 実証: 床を張った当日に2件のバグが出た

[[barefootjs]] には「コンパイラの受理範囲を広げる PR は conformance fixture を同じ PR に含める」という結合ルールがあり、4系統のうち2系統（builtin lowering plugin と sort comparator の形式）は機械的な防壁がなく文章ルール＋レビューだけだった。ここに床を張ったところ:

- レビューのみで運用していた期間に、ある組み込み API が **fixture ゼロのまま出荷されていた**ことが床の初回実行で判明した（レビュー防壁は既に抜けていた）
- 欠けていた fixture を書いた瞬間、コンパイラが**構文エラーの client JS を無警告で出力する**バグが見つかった
- その fixture から自動生成された adversarial なデータ点（マークアップ・マルチバイトの入力）が、Go の `html/template` が href 文脈で値を percent-encode し **JS リファレンスと出力が食い違う**ことを暴いた

fixture が存在しなかった API は、単にテストが薄いのではなく、壊れていても誰も気づけない状態だった。床は「何もテストしていないことに黙って気づけない」状態を潰す装置で、behavioral な保証は個々の fixture が担う。

## 床の後にレビューへ残る仕事

床は fixture の**存在**しか検査できない。レビューに残るのは (1) fixture が拡張の本質を突いた意味のあるものか、(2) どのレジストリも想定しない**新種のカテゴリ**が現れたとき、最初の PR にレジストリ＋床の同梱を要求すること。この2点だけに絞れる。

## 理解度チェック

```quiz
床テストの分子（何がカバーされているか）を、手書きの対応表ではなく計算で導出するのはなぜか。
---
手書きの表は実態と必ずドリフトするから。fixture を実際にコンパイル・解析すれば、その結果自体が「何を検査しているか」の正確な記録になる。
```

```quiz
床テストの allowlist を「縮小専用」にするとはどういう運用か。
---
未カバーを許すエントリは理由付きでのみ追加でき、そのメンバーがカバーされた瞬間 stale としてテストが落ちてエントリ削除を強制される。穴の存在が常に明示的なリストとして残り、黙って増えも残りもしない。
```

```quiz
barefootjs で床を張った初日に見つかった「fixture ゼロの API」は、何を意味していたか。
---
レビューだけで守っていた結合ルールが既に抜けていた証拠。実際にその fixture を書くと、無警告で構文エラーの client JS を出すバグと、Go アダプタの href エスケープ差分が立て続けに見つかった。
```
