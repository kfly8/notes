# Durable Object の WebSocket 接続ごとに許容量を持たせる

サインインなしで使える公開リレー（pedit）で、費用が実際にかかる場所、つまり Room の Durable Object の中で
上限を切った話。

## なぜ IP 単位の制限では足りないか

部屋の作成はステートレスでほぼ無料。費用がかかるのは、Durable Object を起こし続けてメッセージごとに課金される
WebSocket。1本の接続がメッセージを流し続けるだけで Durable Object は眠れず、それは IP 単位のレート制限
（[[workers-rate-limiting-binding]]）では止まらない。接続は1回だけだから。

## 接続ごとの token bucket

- メッセージ数: burst 1000、200/秒で補充。
- バイト数: burst は `最大ピア数 × 最大メッセージ長`（32 MiB）、1 MiB/秒で補充。緩いのは意図的で、新しく
  入った人には全員がドキュメント全体で答えるので、満員の部屋が一斉に再接続しても収まる必要がある。
- 超えたら 1008 で閉じる。ゲストは再接続して再同期する。ホストが閉じられると退出と同じでセッションが終わる
  ので、上限は編集に必要な量よりずっと上に置く。
- `WeakMap` でメモリに持つだけ。Hibernation から起きた部屋は全員が満タンから始まる。

### 最初の値は低すぎた

最初は burst 200、50/秒だった。[[pullfrog]] のレビューが、キャンバスでノードをドラッグすると awareness を
**フレームごと**に発行するので、120 Hz なら3秒未満で枯れると指摘した。144 Hz のドラッグ＋タイピング＋
カーソルより上に置いて、burst 1000・200/秒にした。「編集に必要な量」を見積もるときは、文字入力ではなく
ポインタ追従のような高頻度のイベントを基準にする。

## 同時アップロードの上限

アップロードは1つ丸ごとメモリに持つので、部屋あたり同時に4つまで。超えたら `503` と `Retry-After: 1`。Web
クライアントは既存の `409` と同じように再試行する。Go のホストも最初は 503 を終端扱いしていて、欲しい画像を
黙って諦めていた（レビューで指摘）。5回・500 ms 間隔で再試行し、セッションのキャンセルで止まるようにした。

## テストが CI で揺れた点

- **token bucket のテストに実時間を使わない。** 「補充より速くメッセージが届く」前提は遅い CI ランナーで
  崩れる。Room の時計を差し替えられるようにして、止めた時計で burst ちょうどで切れること、1秒進めながら
  送れば続くことを確かめる。
- **探針が枠を食わない。** 同時アップロードの上限を試すテストが、「4つ目が入ったか」を別の PUT で探って
  いた。その PUT が4つ目の枠を取って、遅い本物の4つ目が 503 になる。Room 自身の進行中カウントを見る。
  単独実行では通り、全体実行で時々落ちる、という出方をする。

## 理解度チェック

```quiz
IP 単位のレート制限があっても、1本の WebSocket 接続が Durable Object の費用を膨らませられるのはなぜか。
---
接続は1回だけなので接続数の制限に当たらず、その後のメッセージはすべて Durable Object に課金される。接続ごとの許容量が要る。
```

```quiz
接続ごとのメッセージ許容量を「編集に必要な量」から決めるとき、何を基準にするか。
---
文字入力ではなく、ポインタ追従のようにフレームごとに発行されるイベント。144 Hz のドラッグで 50/秒は3秒ともたない。
```
