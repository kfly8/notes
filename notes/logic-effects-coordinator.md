# 純粋ロジックと副作用のあるインフラの間には、両方を呼ぶ調整役が要る

「入力を受け取って出力を返すだけの純粋なロジック」と「ネットワーク・DB・ストレージなど、実際に副作用を起こすインフラ」をきれいに分けると、その両方を呼ぶ**第三の種類のコード**が必ず出てくる。「保存する」「ステータスを切り替える」のような、ユーザー操作1つに対応する処理——ロジックで次の状態を決め、インフラでそれを反映し、成功/失敗で違う後始末をする——がこれにあたる。この調整役は、ロジック側にもインフラ側にも自然には属さない。

## 具体例

todoアプリで、「チェックボックスを押すと完了状態を反転し、サーバーに保存する。失敗したら元に戻す」処理を考える。

```ts
// 純粋ロジック: 入力から出力を決めるだけ。副作用を起こさない
function toggleDone(todo: Todo): Todo {
  return { ...todo, done: !todo.done }
}

// インフラ: サーバーとの薄いやり取りだけ
const todoApi = {
  saveTodo: (todo: Todo) => fetch(`/todos/${todo.id}`, { method: 'PUT', body: JSON.stringify(todo) }),
}
```

この2つを組み合わせて実際に動かす処理は、次のようになる。

```ts
async function toggleAndSave(todos: Todo[], id: string): Promise<Todo[]> {
  const target = todos.find(t => t.id === id)
  if (!target) return todos

  const updated = toggleDone(target)                          // ロジックを呼ぶ
  const optimistic = todos.map(t => (t.id === id ? updated : t))

  try {
    await todoApi.saveTodo(updated)                           // インフラを呼ぶ
    return optimistic
  } catch {
    return todos                                              // 失敗したら元に戻す
  }
}
```

`toggleAndSave`は、ロジック(`toggleDone`)とインフラ(`todoApi.saveTodo`)の両方を呼び、「先に反映しておいて、失敗したら戻す」という調整の判断を持つ。これは:

- **純粋ロジック側には置けない** — `todoApi.saveTodo`という副作用を含み、「入力から出力を決めるだけ」という前提を破る。
- **インフラ側には置けない** — 「先に反映して失敗したら戻す」という判断は、サーバーとの薄いやり取りの範囲を超える。`todoApi`自体はいつ何を表示するかを知らないほうが、単体でテストしやすいまま保てる。

`toggleAndSave`は、ロジックとインフラのどちらでもない、調整に徹する第三の場所を必要としている。ここに専用の置き場所を用意していないと、この手の処理は行き場を失い、たいてい一番手近な場所(呼び出し元の画面・ハンドラ)にそのまま書かれる。ユーザー操作の数だけこの手の処理が増えるので、呼び出し元がなし崩し的に肥大化していく。

## 対処: 調整役を独立させる

`toggleAndSave`のような処理を専門に集める場所を1つ作り、ロジックとインフラの両方に依存させる。呼び出し元はここを薄く呼ぶだけになる。

```ts
// operations/toggleTodo.ts
function createToggleTodoOperation(api: TodoApi) {
  return async function toggleTodo(todos: Todo[], id: string): Promise<Todo[]> {
    const target = todos.find(t => t.id === id)
    if (!target) return todos

    const updated = toggleDone(target)
    const optimistic = todos.map(t => (t.id === id ? updated : t))

    try {
      await api.saveTodo(updated)
      return optimistic
    } catch {
      return todos
    }
  }
}
```

コード自体は`toggleAndSave`と同じでも、**独立した場所として名前を持つ**ことが変化点になる。「保存する」「並べ替える」のような処理が増えても全部ここに集まり、呼び出し元はそれを呼ぶだけの薄い状態を保てる。

## この置き場所は「ユースケース」と呼ばれることが多い

「ロジックとインフラの間に調整役が要る」という発想自体は、複数の設計論(レイヤードアーキテクチャを提唱する各種の文献)がそれぞれの用語で語っている——この置き場所は一般に「ユースケース(層)」と呼ばれることが多い。ただし各設計論が定義する厳密な境界線(何が良い実装か、似た名前の別の層とどう違うか、など)は文献ごとに細部が異なり、その定義をそのまま覚えても実務では持ち帰りにくい。

持ち帰る価値があるのは厳密な定義ではなく、「決めるロジックと副作用のあるインフラを分けたら、両方を呼ぶ調整役は自然にどちらにも属さない第三のものになる」という発想そのもの。この発想さえ持っていれば、自分のプロジェクトでその置き場所を`usecases/`と呼ぼうと`operations/`と呼ぼうと`services/`と呼ぼうと構わない——重要なのは名前ではなく、「ここに置く」という決まった場所を1つ持つこと。

## 理解度チェック

```quiz
「ロジックを呼び、インフラも呼び、成功/失敗で違う後始末をする」処理は、なぜ純粋ロジック側にもインフラ側にも置けないのか?
---
純粋ロジック側は副作用(インフラ呼び出し)を持てず「入力から出力を決めるだけ」という前提を破る。インフラ側は「先に反映して失敗したら戻す」のような調整の判断を持つには薄すぎ、単体でテストしやすいという役割を外れる。
```

```quiz
ロジックとインフラを呼ぶ調整役の置き場所を用意していないと、その処理はどこに書かれがちか?
---
一番手近な場所(呼び出し元の画面・ハンドラ)にそのまま書かれる。ユーザー操作の数だけこの手の処理が増えるので、呼び出し元がなし崩し的に肥大化していく。
```
