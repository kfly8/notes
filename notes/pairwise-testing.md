# ペアワイズテスト

独立した「軸」が複数あるとき、全組み合わせ（デカルト積）をテストすると組合せ爆発するので、代わりに
「どの2軸を選んでも、その値のペアが最低1回はどこかのケースに現れる」ことだけを保証する最小のテスト
ケース集合（covering array）を使う手法。全組み合わせの網羅は諦めるが、実務上のバグの大半は2〜3個の
要因が絡んだ時に出るので、費用対効果が高い。

[[barefootjs]] のコンパイラで、JSX の機能同士の組み合わせバグ（単機能のフィクスチャでは踏めない）を
洗い出すために実装して使った。具体的には5軸・各5〜12値のグリッド（state × structure × binding ×
event × callback）で、フルカーテシアン積なら万単位のケース数になるところを、t=2 の covering array
なら **97 ケース**で済んだ。

## covering array の作り方（greedy 構成）

1. まだどのケースにも登場していない「軸ペア×値」の組を1つ選ぶ（例: `structure=keyed-loop` と
   `event=ref-callback` のペア）。
2. それを種にして、残りの軸を1つずつ埋めていく。各軸で「新たにカバーできるペア数が最大になる値」を
   貪欲に選ぶ。同点なら乱数（ケースIDから決定的にシードした擬似乱数）でタイブレークする——毎回同じ
   ケース列が再現されることが、失敗の再現性のために重要。
3. 全ペアがカバーされるまで1〜2を繰り返す。

この貪欲法は最適（理論最小）ではないが、実装が単純で、決定的に再現でき、既存のケース列を壊さずに
後から強度を上げる拡張がしやすい。

## t=3 への部分昇格（variable-strength coverage）

全軸を一律に t=3（3つ組ペアを全部カバー）に上げると、ケース数がさらに跳ね上がる。barefootjs では
「バグを踏んだ実績が多い軸」だけを狙って t=3 に昇格する設計にした——issue トラッカーの履歴を見て、
ループ構造・イベント・コールバック形状の3軸が壊れやすいと分かっていたので、この3軸のうち2軸以上を
含む軸の組だけ t=3 に昇格させた。

- 7 / 10 通りの軸の組が対象になった。
- 対象範囲の妥当な値の3つ組は 1849 通り。
- 既存の t=2 の97ケースが、そのうち594通りをたまたま満たしていた。
- 残り1255通りを埋めるために354ケースを追加し、計451ケースになった。

ここで大事なのは、**既存の t=2 の97ケースを1件も動かさなかった**こと。後から強度を上げるとき、
既存ケースを再生成・並べ替えすると、そのケースを指す ID がずれて、個別に調査済みの既知不具合の
記録（後述の quarantine）が総崩れになる。既存分はそのまま、足りない分だけ追記する構成にすることで、
過去の調査結果を壊さずに強度を上げられる。

## オラクル: 正解を書けないテストの判定基準

ペアワイズ生成したケースは組み合わせ数が多すぎて、人間が一つずつ「正しい出力」を書けない。代わりに
**内部矛盾の検出**を判定基準にした。

- **three-point agreement**: 同じ状態を (1) サーバーでレンダーしてそのまま表示、(2) サーバーでレンダー
  してからクライアント側でハイドレーション、(3) クライアント側だけで最初から構築、の3通りで作り、
  DOM の状態（`selectedIndex` や `.value` など、マークアップ文字列ではなく実際のプロパティ）が
  3つとも一致するはずだと確認する。
- **hydration snap 検出**: ハイドレーションの前後でユーザーに見える状態が変わってはいけない。
- **操作の冪等性**: 何か操作したあとの DOM と、その結果の状態を最初からレンダーし直した DOM が
  一致するはず。

「正解データがなくても、複数の経路が食い違わないことは検証できる」という考え方は、生成テスト全般に
応用が効く。[[gleam-compiler-fuzzing]] では逆に、生成した AST という第三の情報源から期待される出力を
機械的に導出できるケースで、それをオラクルにしていた。

## quarantine: 見つかった不具合を握りつぶさずに可視化する

大量にケースを生成すると、直っていない既知の不具合も一緒に検出され続ける。CI を毎回赤くするわけには
いかないので隔離するが、やり方が重要だった。

- 「`event=ref-callback` を含むケースは全部スキップ」のような**パターン一致でのスキップは禁止**。
  パターンは直った分もまとめて隠してしまい、静かにブランケットスキップに劣化する。
- 代わりに、失敗した**ケースIDと判定項目の組を1件ずつ**登録する。1つの根本原因が30件のケースで
  出ていれば、理由を共有した30件のエントリを書く。
- 登録したペアが**直ったら自動で気づける**ようにする。「そのケースはまだ失敗しているはず」という
  逆方向のアサーションを張っておき、実は直っていたら「このエントリは陳腐化しています、消してください」
  と教えてくれるようにする。直った不具合の記録が消し忘れで残り続ける事故を防げる。

## 理解度チェック

```quiz
なぜ pairwise (t=2) covering array は、全組み合わせのデカルト積より優先されるのか？
---
実務のバグの大半は少数（2〜3個）の要因が絡んで起きるため、全網羅を諦めて「どの2軸のペアも
最低1回は出現する」ことだけを保証すれば、ケース数を大きく減らしつつ多くのバグを検出できるから。
```

```quiz
t=2 の covering array に後から t=3 の強度を追加するとき、既存ケースを再生成してはいけないのはなぜか？
---
既存ケースを指すIDがずれて、それらのケースについて個別に調査・記録していた既知不具合の
台帳（quarantine）が総崩れになるから。既存分はそのまま残し、足りない分だけ追記する。
```
